## Задача: примитивная админ-панель (этап 1)

Это самый первый этап разработки приложения. Цель этапа — добиться **стабильной** загрузки
файлов на сервер и их получения пользователем как на ПК, так и на смартфоне. Никакого
конструктора уроков на этом этапе нет — только файлы.

Два таба: **Пользователь** и **Админ**.

### Таб «Пользователь»
- Видит только файлы, которые есть на сервере.
- Может воспроизвести: фото (просмотр), видео (воспроизведение), аудио (воспроизведение).

### Таб «Админ»
- Создаёт строку → выбирает файл с ПК.
- В строке видно: выбранный файл, вес файла (столбец), статус (на сервере / нет), время
  загрузки на сервер.
- Может удалить файл с сервера прямо из строки.
- **Все изменения применяются только после нажатия главной кнопки «Синхронизировать с
  сервером»** — выбор файла и удаление до этого момента — локальное, неподтверждённое действие.
- Кнопка «Активировать дебаг» — включает подробные логи в консоли: как файл уходит от админки,
  как файл загружается у пользователя, время загрузки и т.д.

## Архитектурное решение на будущее: предзагрузка во время пауз сценария (2026-06-16)

В чат-сценарии уже есть искусственные паузы между сообщениями (задержки для реалистичности
диалога — «вы присоединились» → пауза → «учитель присоединился» и т.п., см. триггеры
`after_delay`/`startDelay` в старом проекте). Идея: использовать эти и так существующие паузы
как окно для фоновой подгрузки медиафайлов из следующих 1–3 сообщений вперёд — пока пользователь
читает текущее сообщение, следующие файлы тихо скачиваются и кэшируются. К моменту, когда
сценарий доходит до них, показ происходит мгновенно, без видимого лага.

**Не проверено:** сколько файлов реально успевает подгрузиться за типичную паузу (3–5 сек) на
настоящем 3G — наш тест замерял только скорость маленького JSON-запроса (пара КБ), не скорость
скачивания самого файла (фото/видео — сотни КБ — несколько МБ). Нужен отдельный тест: скачать
реальный файл из R2 на 3G и замерить КБ/сек, чтобы рассчитать, сколько секунд паузы нужно на
сколько файлов вперёд.

### Финальная схема (согласовано 2026-06-16)

Тест на реальном 3G показал: каждый новый запрос «стоит» ~2.2 сек на установку соединения почти
независимо от размера файла (32 КБ и 1.9 МБ грузились за одинаковое время) — то есть упираемся
не столько в скорость канала, сколько в задержку на старте каждого файла.

Прямое использование текущего механизма (полная докачка в `Blob`, строго по очереди) для
финального чата опасно тремя вещами: (1) память — блобы копятся вечно; (2) если очередь не
успела — пользователь видит пустую заглушку вместо файла; (3) один зависший файл блокирует всю
очередь позади себя. Договорились так:

- **Фоновая предзагрузка** (текущий механизм: очередь + ретраи) — только для сообщений,
  которые ещё не показаны, заранее, во время пауз сценария.
- **Текущее показанное сообщение**, если для него ещё не готов blob — не ждать его, а сразу
  отдать нативный `<video>/<audio> src=...>` напрямую (браузер сам стримит с буферизацией).
  Хуже, чем мгновенный blob, но не зависание.
- **Лимит памяти: держим в памяти blob'ы только последних 5 сообщений** (скользящее окно),
  более старые — выгружаем (`URL.revokeObjectURL` + убираем из state). Важно для слабых
  Android-телефонов с небольшим объёмом RAM — лесон с 20+ медиафайлами по 2-3 МБ не должен
  копиться в памяти целиком.
- **Зависший файл не должен стопорить очередь навсегда** — нужен потолок ожидания, после
  которого очередь идёт дальше, а зависший файл продолжает попытки в фоне отдельно.

**Когда делать:** часть следующего этапа (чат-плеер), не текущей админ-панели.

### Реализовано в табе «Пользователь» как прототип/тест (2026-06-16)

Уточнения к схеме выше, добавленные после теста и реально закодированные (не только описаны):

- **Фото никогда не выгружаются** — пустое фото в чате выглядело бы как явная дыра, а фото
  занимают не так много памяти, как видео. Лимит буфера (5) считается только для видео/аудио.
- **Видео при выгрузке не пропадает совсем** — перед удалением тяжёлого blob'а захватывается
  один кадр (через скрытый `<video>` + `<canvas>`) и остаётся как стоп-кадр вместо пустоты.
- **Буфер на 5 видео/аудио, вытеснение — по дистанции от текущей позиции в чате**, не по
  времени загрузки. Пример: в буфере 20-24 (текущая позиция ~24), пользователь подгружает
  №10 по требованию → вытесняется №20 (он дальше всех от 24). Дальше пользователь подгружает
  №2 → должен вытесниться №10 (он теперь дальше всех — 22 шага от текущей позиции против 3-4
  у 21-24), а не №21 просто потому что он «дольше всех висит» (первая версия буфера ошибочно
  вытесняла именно по этому принципу — поправлено).
- **Подгрузка по требованию**: клик на выгруженный файл (стоп-кадр видео или плейсхолдер
  аудио) запускает повторную загрузку этого конкретного файла через тот же механизм
  (очередь/повтор); попав в буфер, такой файл сам станет первым кандидатом на вытеснение,
  если позиция в чате не сдвинется к нему.

**Найденные и исправленные ошибки (тест на Android, 2026-06-16):**
1. Предзагрузка прогоняла весь список файлов почти мгновенно (22 файла за ~17 сек), не
   обращая внимания на то, что показ на экране идёт по одному каждые 3 сек. Буфер на 5
   успевал заполниться и провернуться несколько раз ещё до того, как пользователь реально
   дошёл до этих сообщений. Фикс: предзагрузка теперь не уходит дальше, чем на
   `PREFETCH_LOOKAHEAD = 3` сообщения вперёд от уже показанного (параметр `allowUpTo`).
2. Вытеснение было устроено как FIFO («кто дольше висит в буфере») — из-за этого подгрузка
   старого сообщения по требованию вытесняла случайное соседнее свежее сообщение, а не саму
   себя при следующей подгрузке. Заменено на вытеснение по дистанции от текущей позиции
   (параметр `currentIndex`) — буфер теперь всегда защищает то, что рядом с «живым краем»
   чата, а не то, что просто недавно подгрузилось.

Это пока живёт в табе «Пользователь» как полигон для теста на слабом Android — перенос в
реальный чат-плеер (с нативным стримингом для «текущего» сообщения) — следующий этап.

## Система уроков — концепция (2026-06-17)

### Идея

Урок = цепочка нод на canvas-холсте. Каждая нода — одно сообщение в чате (аудио, фото, видео,
текст). Между нодами — переходы по триггерам: «если [событие] → тогда [следующая нода]».
Граф сохраняется на сервер как JSON. Клиент скачивает его один раз и запускает state machine
локально — серверная логика триггеров не нужна (урок детерминирован).

### Что хранится на сервере

Таблица `lessons` (добавить в `supabase_schema.sql`):
```
id uuid, title text, script jsonb, created_at timestamp
```

`script` — один JSON-документ:
```json
{
  "nodes": [
    {
      "id": "n1",
      "x": 120, "y": 80,
      "type": "audio",
      "file_id": "uuid",
      "triggers": [
        { "if": "played",          "then": "n2" },
        { "if": "timer", "ms": 3000, "then": "n3" }
      ]
    }
  ]
}
```

Файлы (аудио/фото/видео) не дублируются — ноды ссылаются на существующую таблицу `files`.

### Три размера ноды

| Размер | Что видно |
|--------|-----------|
| **nano** | Только порядковый номер ноды. Цвет фона по типу: фото = мягкий зелёный, аудио = мягкий синий, видео = мягкий фиолетовый, текст = нейтральный серый |
| **mini** | Порядковый номер + название типа (из выпадающего меню типа) |
| **max** | Порядковый номер + выпадающее меню типа («Текстовое / Голосовое / Фото / Видео сообщение») + триггеры: «Если» и «Тогда» — кастомные выпадающие меню как в старом `BlockEditorChat.jsx` |

Переключение между размерами — кликом на ноду (nano → mini → max → nano).

### Типы триггеров «Если»

| ID | Описание |
|----|----------|
| `played` | Аудио/видео прослушано до конца |
| `timer` | Прошло N секунд с момента появления ноды |
| `timer_after_play` | Прошло N секунд с момента окончания воспроизведения |
| `photo_shown` | Фото появилось на экране |

«Тогда» — всегда выбор существующей ноды из списка.

### Canvas-страница

Открывается поверх вкладок (простое переключение страниц в `App.jsx`, без роутера).
Верхний левый угол — кнопка-заглушка (будущие настройки урока).
Соединения между нодами — bezier-кривые с органическим wobble (`neuronPath` из старого проекта).
Узлы перетаскиваются. Холст панорамируется.

## Новая задача: Layout-система чата (плеер)

### Принцип

Чат живёт на `flex-direction: column-reverse`. Это даёт:
- Первое сообщение всегда у низа экрана
- Каждое новое сообщение появляется снизу, старые уходят вверх
- Пузырь при росте высоты (перенос текста) расширяется вверх, не вниз
- `scrollTop=0` всегда = виден низ чата, никакого JS `scrollToBottom`

Панели снизу (`ChooseWord`, `PhraseAssembly`) — flex-сиблинги под фидом.
При появлении панели фид сжимается, история автоматически смещается вверх.

Анимация панели: IN — система монтирует + CSS slide-up. OUT — модуль сигналит `onDone()` →
система ставит `exiting` → CSS slide-down → после `transitionEnd` система размонтирует.
Модуль не знает о своей анимации ухода.

```
┌─────────────────┐
│   PlayerTopBar  │  flex-shrink: 0
├─────────────────┤
│                 │
│   PlayerFeed    │  flex: 1 · column-reverse · overflow-y: auto
│   (история ↑)   │
│                 │
│  [последнее]    │  ← всегда у низа фида
├─────────────────┤
│  BottomPanel    │  flex-shrink: 0 · высота авто · slide-up анимация
└─────────────────┘
```

### Шаг 6 — Easy-bounce (лёгкое пружинящее покачивание)

**Что делаем:**
- Заменяем `ease` на кастомный `cubic-bezier` с лёгким перелётом (overshoot):
  - Slide-up: `cubic-bezier(0.34, 1.20, 0.64, 1)` — чуть вылетает вверх и оседает
  - Slide-down: `cubic-bezier(0.36, 0, 0.66, -0.10)` — лёгкий уход с подтяжкой
- Длительность: slide-up ~320ms, slide-down ~260ms (уход быстрее — так ощущается живее)
- **Только `transform` и `opacity`** — GPU-ускорение, нет layout/paint
- `will-change: transform` на `.bottomPanel` — подсказка браузеру заранее

**Важно по оптимизации:**
- Никаких анимаций `height`, `padding`, `margin` — только `transform`
- Чат сжимается не анимацией высоты панели, а тем что панель в потоке (`flex`)
  и появляется мгновенно по высоте (только transform двигает её визуально)
- На слабых телефонах `prefers-reduced-motion` → убираем bounce, оставляем simple ease

**Файлы:** `panels.css`

**Тест:** смотреть на реальном телефоне — покачивание должно быть едва заметным,
не агрессивным. Проверить в Chrome DevTools → Performance что нет layout thrash.

## Пользовательский интерфейс: видео-лента (концепция согласована 2026-07-05)

### Суть
Приложение встречает пользователя вертикальной видео-лентой (как TikTok).
**Одно видео = одна фраза = один модуль** (`curricula`). Уроки внутри модуля —
слова этой фразы. Кнопка «Изучить фразу» на видео ведёт на схему модуля
(Старт → уроки-слова → Финал — уже готова, `ModuleGraph`). Существующее ядро
(плеер, XP, анализ знаний, редактор) не трогаем — меняется только обёртка.

### Навигация
- Нижний бар: **[Уроки]** (лента) · **[Профиль]**; для `is_admin` — третья
  иконка «Админ» (текущие админ-вкладки + canvas-редактор, пользователи её не видят).
- Поверх ленты сверху две вкладки: **(Рекомендации)** | **(Мои уроки)**.
- Рекомендации — все опубликованные модули-видео.
- Мои уроки — начатые модули; два режима: видео-скролл (без HUD справа, снизу
  прогресс-бар модуля) и список (строки модулей с % прохождения).

### Экран видео в ленте
- Видео фразы на весь экран, автоплей; звук — по первому тапу (оверлей
  «включить звук», как TikTok Web: браузер блокирует autoplay со звуком).
- Справа HUD: лайк · закладка · репост. Кнопка «Изучить фразу» → схема модуля.
- Гость смотрит ленту без ограничений; может пройти диагностику и первый урок
  бесплатно, дальше — регистрация. Тап гостя по лайку/закладке → форма входа.

### Профиль
- Не залогинен → форма входа/регистрации (`AuthTab`).
- Залогинен → уровень, XP-бар; под ними вкладки: Сохранённые уроки ·
  Пройденные уроки · Копилка слов; ⚙ настройки в правом верхнем углу.
- **Копилка слов = названия пройденных уроков между Стартом и Финалом**
  (считается из `lesson_results` + структуры модулей, новых таблиц не нужно).
- Пустые «Мои уроки» — подсказка «можешь начать обучение» + кнопка в ленту.

## Сложность фразы на слух — краудсорсинг (решения 2026-07-09)

### Суть
У каждого видео-фразы в ленте — иконка сложности (три полоски-«сигнал»),
она же кнопка голосования. Тап → панель выезжает от кнопки (scale от 0 +
рост в ширину). Один вопрос — «Понял на слух?»: 🟢 Легко (с первого раза) ·
🟡 Средне (переслушал/частично) · 🔴 Сложно (открыл текст). Чипы-причины
(быстрая речь, незнакомые слова) — НЕ в первой версии.

### Правила (согласованы)
- Голос перезаписываемый, бессрочный; одна строка на (user, module).
- Итог = **медиана** явных голосов; хранится денормализованно на
  `curricula.difficulty` + `difficulty_votes` (пересчёт триггером БД при
  каждом голосе — лента/фильтр не агрегируют на лету).
- До ~5 голосов иконка серая («мало оценок») — порог на клиенте
  (`MIN_DIFFICULTY_VOTES`), один голос фразу не красит.
- В панели голосования чужое распределение не показывается — только свой
  выбор (анти-якорение). Тап по кружку применяет голос, тап вне — закрывает.
- В «Моих уроках» иконка показывает **свой голос в приоритете** (иначе общий);
  голосовать можно и там — та же запись в БД.
- Гость: тап по голосу → форма входа (как лайк).

### Неявные сигналы (этап 3, потом)
- Снимок «первой встречи» с фразой: проигрывания + открыл ли текст; после
  первого сеанса замораживается навсегда (повторные просмотры не считаются).
- Учитывается ТОЛЬКО от непроголосовавших, малым весом (~0.3), как паттерн
  (переслушал И открыл текст = сильный сигнал), а не одиночное событие.
- Явный голос всегда важнее: проголосовал — его неявные сигналы выкидываем.

### Фильтр по сложности (этап 2, потом)
- Одна глобальная кнопка: маленькая, справа в шапке; состояние общее для
  «Рекомендаций» и «Моих уроков», запоминается.
- Панель с той же анимацией; мультивыбор 🟢🟡🔴; «все выключены» = «все
  включены».
- Рекомендации: фильтр по общей оценке + подмешивание серых фраз ~1 из 5–7
  (холодный старт новых фраз). «Мои уроки»: фильтр по своему голосу (иначе
  общий), серые видны всегда.

### Этапы
1. **БД + голосование в ленте** (иконка, панель, свой голос) — в работе.
2. Фильтр в шапке.
3. Неявные сигналы первой встречи; позже — взвешивание по уровню ученика.

## Супергонка + вкладка «Рейтинг» + достижения (решения 2026-07-09)

### Супергонка — суть
Еженедельное соревнование по выходным (сб+вс), пройти можно один раз.
Спец-страница гонки: тема (жизненная ситуация — «буйный таксист»,
«доставщик задерживается»...), порог XP для открытия, список заданий
(ссылки на готовые уроки — визуально как «Мои уроки» в режиме списка),
сверху крупный вход в саму гонку.

### Админ-конструктор гонки
- Аналог графа урока, но без Старта и без линий: просто упорядоченный
  список уроков, которые админ выбирает из готовых уроков приложения
  (ссылки, не копии). Порядок можно менять.
- Порог XP открытия = сумма XP добавленных уроков (XP уже указан в уроках).
- Панель управления: время запуска, продолжительность, расписание
  пуш-уведомлений (анонс/старт/окончание), показ итогов всем.

### Путь пользователя
1. Попап «Поздравляем, доступна еженедельная супергонка» — раз в неделю,
   при первом завершении любого модуля на этой неделе (за ~неделю до гонки).
   Кнопка «Узнать подробнее» → страница гонки.
2. Проходит уроки списка, набирает порог XP → гонка открыта.
3. Прошёл все уроки → остаётся таймер до старта + подписка на пуш о старте.
4. Сб-вс проходит гонку. Прерывание (звонок/батарея) НЕ сжигает попытку:
   прогресс сохраняется, можно продолжить до конца воскресенья; время
   считается только внутри заданий, пауза между ними в зачёт не идёт.

### Подсчёт и итоги
- Один подиум: сортировка по минимуму ошибок, при равенстве — по времени
  (время — только тай-брейкер, чтобы таймер не давил).
- На выходных живой таблицы НЕТ — интрига до понедельника.
- По окончании гонки всем участникам попап: строки мест 1-2-3; если
  пользователь не в тройке — его строка чуть ниже с отступом.
- В итоговой таблице публично только место и очки; свои ошибки и время
  каждый видит только на своём экране результата.

### Достижения (3 шт) и косметика — 1 достижение = 1 вид
| Достижение | Условие | Открывает |
|------------|---------|-----------|
| 10-й уровень | достичь 10-го уровня | подложка под ник |
| Участник гонки | финишировал все задания гонки | рамка вокруг аватара |
| Победитель гонки | топ-3 подиума | медаль у аватара с цифрой 1/2/3 |

Пользователь навешивает открытое в любой комбинации и видит предпросмотр,
как он выглядит в глобальном рейтинге.

### Вкладка «Рейтинг» (новая, в нижнем баре)
- Глобальный рейтинг по XP **за всё время**: строка = аватар (+рамка,
  +медаль), ник (на подложке), уровень.
- Сверху — баннер-вход текущей супергонки (тема, прогресс XP, таймер).
- Субвкладка «Достижения»: список трёх достижений + примерка косметики.

### Технические решения
- Уровни: расширить `xpLevels.js` до 10-го — пороги 5:1600, 6:2400,
  7:3400, 8:4600, 9:6000, 10:8000 XP (названия — предложить на утверждение).
- Ники/аватарки: в `user_profiles` их нет → добавить `nickname`
  (по умолчанию из имени регистрации, редактируется в профиле);
  аватар — кружок с первой буквой и цветом от id (без загрузки фото).
- RLS позволяет читать только свой профиль → для рейтинга нужна публичная
  выборка (view/RPC c ником, XP, уровнем, косметикой — без email и прочего).
- Итоги гонки, медали, попап результатов — серверный пересчёт по окончании
  (по аналогии с pg_cron у пушей).

## Золотые билеты + подсказки Финала (решения 2026-07-11)

### Экономика (согласовано)
- **Золотой билет** — топ-валюта. Выдаётся за прохождение Финала модуля
  максимум с **3 подсказками**. Подсказка = ПЕРВОЕ раскрытие перевода
  конкретного сообщения (повторное раскрытие того же — бесплатно).
  Больше трёх — раскрывать не запрещено, но билет в этой попытке не выдаётся.
- **1 модуль = 1 билет навсегда** (реестр `module_tickets`) — редкость
  гарантирована структурно: билетов не больше, чем модулей. Не вышло —
  пересдавай Финал сколько угодно, билет с модуля всё равно единственный.
- **Вход в супергонку = 80% XP подготовки И 1 билет.** Билет списывается
  в попапе-шлагбауме кнопкой «Открыть доступ» (RPC `start_race`, работает
  с анонса до конца гонки), дальше вся гонка без доплат — повторные входы
  бесплатны (`race_ticket_spends`); админ — бесплатно. Кнопка «Начать
  супергонку» зовёт тот же RPC как страховку для путей в обход шлагбаума
  (попап-анонс) — идемпотентно.
- **0 подсказок** = достижение «Чистый финал» (`clean_final`, выдаётся и при
  пересдаче) → открывает **золотую подложку** под ник (`cosmetics.bg2`).
- Верхняя панель (hudBar, ShellV2): уровень · билеты 🎟 · энергия ⚡.
- Баннер гонки в «Рейтинге»: строка «Вход: 1 золотой билет»; тап по баннеру →
  попап-шлагбаум (RaceTicketGate): стоимость, свой баланс, как заработать.
  Кнопка «Открыть доступ» списывает билет и открывает страницу гонки; без
  билета кнопки нет. Вход свободный (кнопка «Войти», билет не тратится):
  админ · гонка завершена · уже финишировал · доступ уже оплачен.
  Попап-анонс недели («Узнать подробнее») открывает страницу напрямую —
  осознанно: там билет спишется при старте супер-урока.
- Анти-чит v1: число подсказок серверу присылает клиент — тот же осознанный
  компромисс, что у времени/ошибок гонки. Баланс билетов живёт только на
  сервере (`user_profiles.tickets`, все изменения через SECURITY DEFINER RPC).

### Звёзды обычных уроков — реализовано (2026-07-11, v3.2.820)
- 1–3 звезды по неверным ответам за прохождение: 3★ — 0 ошибок, 2★ — 1–2,
  1★ — пройден. Ошибки считает свой счётчик плеера (независим от recordStats —
  пересдача «без записи» не дарит 3★). Только уроки между Стартом и Финалом.
- Чистая косметика: на доступ к Финалу не влияют. Хранится ЛУЧШИЙ результат.
- Хранение: сервер `lesson_results.stars` (RPC `save_lesson_stars`, только

- Показ: экран итогов урока (StarsBlock) + карточки уроков схемы модуля
  (MgStars вместо «Пройдите и получите» у пройденных).
- **SQL**: блок «Звёзды обычных уроков» в `supabase_schema.sql` (колонка +
  RPC). Без него клиент не ломается: RPC вернёт ошибку → best=0, звёзды
  живут локально.

## Telegram Mini App — план интеграции (2026-07-11, не начато)

Цель: приложение открывается ПРЯМО ВНУТРИ Telegram — пользователь из
телеграм-канала владельца нажимает «Открыть приложение» и попадает в Pithy
без браузера. Технология: Telegram Mini Apps (WebApp) — тот же наш сайт
с Vercel, обёрнутый мини-аппом бота. Отдельного билда НЕ делаем: одна
кодовая база, Telegram определяется на лету.

Каждый этап — самостоятельное ТЗ. Общие правила из CLAUDE.md обязательны
(русский, APP_VERSION при изменении кода, STRUCTURE.md, лимиты строк,

### Как это устроено (справка для исполнителя)
- Мини-апп привязывается к боту. Ссылка вида `t.me/<имя_бота>/<имя_аппа>`
  публикуется в канале — Telegram сам рисует карточку с кнопкой «Открыть
  приложение». Внутри открывается наш URL (https://pithy-app.vercel.app).
- В мини-аппе доступен объект `window.Telegram.WebApp` (подключается
  скриптом `https://telegram.org/js/telegram-web-app.js`): initData
  (подписанные данные пользователя TG), управление высотой/жестами/кнопкой
  «Назад», тема.
- На телефонах мини-апп живёт в webview (не iframe), в Telegram Desktop и
  web.telegram.org — в iframe. ⚠️ ВАЖНО: этап 2 плана стабилизации
  предлагает `X-Frame-Options: DENY` — это СЛОМАЕТ Telegram Web. Вместо
  него использовать CSP `frame-ancestors 'self' https://web.telegram.org`
  (X-Frame-Options не ставить вовсе). Если этап 2 уже выполнен — поправить
  vercel.json в рамках этапа TG-1.

## Ежедневный стрик + окно наград (решения 2026-07-12, в разработке)

### Суть
Стрик = число дней подряд, когда пользователь ЗАХОДИЛ в приложение (загрузка
приложения, не привязано к прохождению урока). Несколько заходов в один день
считаются одним. За каждый день — начисление в **основной XP** (не отдельная
валюта): 5 XP за обычный день, крупные бонусы за вехи. Получение — **только
вручную**, кнопкой «Забрать награду» в полноэкранном попапе (макет прислан
пользователем — вертикальный путь дней, hero-прогресс до следующей вехи).

### Вехи наград (конфиг в БД, не в коде)
| День | Награда |
|------|---------|
| 1..6, 8..14, 16..29 (не веха) | 5 XP |
| 7 | 150 XP |
| 15 | 300 XP |
| 30 | 500 XP + 1 золотой билет |
| 37, 45, ... | доп. приз (по той же аналогии, точные числа/награды до дня
  182 донабить позже — не блокирует остальную разработку) |
| 182 (полгода) | спецокно + 2 золотых билета |
| 365 (год) | 3 золотых билета |

Хранится в таблице `streak_milestones` (day_number, xp_reward, ticket_reward,
label) — день не из таблицы получает дефолт 5 XP. Редактируется админом прямо
из приложения (вкладка «Админ»), а не правкой SQL — см. этап 8 ниже.

### Заморозки (обе — за золотые билеты)
- **Заморозка** — покупается заранее, **не стакается** (можно иметь только
  одну про запас). Хранится как флаг `has_freeze_charge boolean`. Молча
  списывается сервером в `touch_daily_login`, когда обнаружен пропущенный
  день — спасает стрик без участия пользователя.
- **Авто заморозка** (обычный пользователь) — покупка даёт защиту на **2
  пропущенных дня** (`auto_freeze_charges_left`), повторная покупка
  недоступна, пока пул не обнулится.
- **PRO** — тот же эффект включён навсегда бесплатно: суббота и воскресенье
  всегда прощаются + 1 будний день в неделю прощается автоматически.
- Тап обычного пользователя на кнопку «Авто заморозка» без покупки — шторка
  с объяснением механики + предложение оформить PRO.

### Показ окна наград
- Полноэкранный попап (не блок в профиле) — **раз в день, после первого
  пройденного урока за этот день**.
- Ручной вход — блок «Ежедневные награды» в профиле, открывает тот же попап
  в любой момент.
- В рейтинге — маленький значок 🔥 с числом дней рядом с ником (виден всем).

### Защита от накрутки
Всё серверное: баланс XP/билетов/заморозок живёт только в `user_profiles`,
все изменения — через SECURITY DEFINER RPC (как `spend_energy`/`complete_lesson`),
клиент не передаёт суммы. `streak_milestones` — RLS `select` всем,
`insert/update/delete` только `is_admin()` (тот же паттерн, что у `curricula`/
`races`) — обычный пользователь не может изменить награды даже прямым
запросом в обход интерфейса.

### Этапы разработки
1. БД: колонки `user_profiles` + таблица `streak_milestones` + RPC
   (`touch_daily_login`, `claim_streak_reward`, `buy_streak_freeze`,
   `buy_auto_freeze`) + `get_leaderboard` с `current_streak`.
2. Клиент: `streakApi.js` + вызов `touchDailyLogin()` при загрузке приложения.
3. Рейтинг: значок 🔥N у ника в топе.
4. Профиль: блок «Ежедневные награды» (статус + кнопка попапа).
5. Попап наград по макету: hero-прогресс, путь дней, «Забрать награду».
6. Автопоказ попапа раз в день после первого урока.
7. Кнопки заморозки/автозаморозки в попапе + explainer-шторка для обычных.
8. Админ: вкладка редактирования `streak_milestones` прямо из приложения.
9. Пуши: `push_audience_evening()` — переписать на реальный
   `current_streak`/`last_active_date` вместо текущей эвристики по
   `lesson_results`; число дней подряд — в текст шаблона.

### Стрик v2 — пояса, автоклейм, «Забрать всё», пуш вехи (решения 2026-07-16)
Реализовано (SQL-блок «Стрик v2» в supabase_schema.sql + клиент + push-trigger):
- **Часовой пояс устройства**: граница суток стрика — пояс телефона
  (`Intl.DateTimeFormat().resolvedOptions().timeZone` → `user_profiles.tz`),
  VPN не влияет (пояс из настроек ОС, не из IP). Невалидный пояс от клиента
  отбрасывается сервером.
- **Анти-накрутка**: новый день серии засчитывается не чаще, чем раз в 12
  реальных часов (`last_streak_increment_at`); «слишком ранний» заход
  помечает день посещённым (серия не сгорает), +1 придёт со следующим днём.
  Сдвиг пояса назад (отрицательный gap) серию не роняет.
- **Автоклейм**: при сбросе серии незабранные награды не сгорают — сервер
  начисляет их сам; клиент показывает плашку «Серия N дн. прервалась,
  начислено +X XP» в окне наград (localStorage `pithy_streak_reset_info`).
- **«Забрать всё»**: RPC `claim_streak_rewards_all()` начисляет все
  накопленные дни одной операцией; кнопка в попапе при 2+ незабранных днях.
- **Пуш «накануне вехи»** (`streak_milestone_eve`): вечером тем, кто сегодня
  уже заходил и у кого завтра день-веха — «Завтра 7-й день, ждёт 150 XP».
  Плейсхолдеры шаблона: {streak} {day} {xp} {tickets}.
- **Почасовой вечерний cron**: `push_audience_evening()` сама выбирает тех,
  у кого в их поясе сейчас 19:xx; дедупликация — по локальной дате.
- Цены заморозок остаются в SQL (решение: в админку не выносить).

Чек-лист деплоя (руками, по порядку):
1. Применить в Supabase SQL-блок «Стрик v2» из `supabase_schema.sql`
   (без него клиент шлёт неизвестный параметр p_tz — touch упадёт).
2. Задеплоить edge-функцию: `supabase functions deploy push-trigger
   --no-verify-jwt`.
3. pg_cron: job вечернего пуша перевести с «раз в день 19:00 МСК» на
   каждый час — schedule `0 * * * *`, тот же POST `{ kind: "evening" }`
   с заголовком x-cron-secret (job энергии не трогать).
4. В админке (Пуши → шаблоны) создать шаблон с триггером
   «завтра веха серии» (`streak_milestone_eve`).

### Стрик v3 — день закрывает УРОК + полноэкранное окно (решения 2026-08-31)
Миграция `supabase/migrations/20260831120000_streak_by_lesson.sql` + клиент
(`src/features/streak/`). Главное изменение смысла: раньше день серии
засчитывался за сам факт захода (открыл-закрыл — +1).

- **День закрывает урок**: `bump_streak_on_lesson()` зовётся из `useLessonFinish`
  после `complete_lesson`; идемпотентна в пределах суток. Защита «не чаще
  раза в 12 реальных часов» переехала с захода сюда.
- **Сгорание — по `last_lesson_date`**, новой колонке (бэкофилл из
  `last_active_date`, старые серии сохранены целиком). Иначе «захожу
  каждый день, уроков не прохожу» дало бы бессмертную серию.
- **При сбросе `current_streak = 0`** (было 1): сегодняшний урок ещё не
  пройден. `touch_daily_login` больше не наращивает серию — только визит,
  пояс и судьба серии (заморозки/PRO/сброс с автоклеймом).
- **Полноэкранное окно раз в сутки** (`StreakGateOverlay`): показывать или нет
  решает СЕРВЕР (`first_today`), а не localStorage — очистка кэша, второй
  браузер или переустановка PWA иначе давали повторный показ. Состояния:
  `grown` / `saved` (спасла заморозка или PRO) / `reset`. Новичку без серии и
  на нуле после уже показанного срыва окно не показывается.
- **Момент показа**: окно монтируется ещё под стартовым сплэшем — лого
  улетает на готовое окно. Лента ставится на паузу ТОЛЬКО после события
  `pithy:splash-gone` (index.html): сплэш снимается по первому кадру видео, и
  на паузе лого висело бы до страховки в 3.5 с. Ответ сервера позже 4 с —
  окно не показываем вовсе (кроме срыва), чтобы не выдёргивать из видео.
- **PWA сутками не перезагружается** (на iPhone его сворачивают): по
  `visibilitychange` со сменой локальной даты визит отмечается заново —
  раньше новый день в такой сессии не засчитывался вообще (баг стрика v2).
- **Защиты в окне**: одна строка и максимум один CTA, приоритет — как на
  сервере (PRO → заморозка → авто-заморозка). Сработавшая защита — главный
  сюжет экрана (раньше о ней не сообщалось нигде); `pro_weekday` дописывает
  «на этой неделе больше не сработает». На экране срыва CTA выбирается по
  причине: пропуск 1 день → заморозка, выходные у не-PRO → PRO, 3+ дней →
  ничего (защита всё равно бы не спасла). Напоминание «серия не защищена» —
  от 5 дней и не чаще раза в неделю.
- Плашка `StreakDailyToast` в схеме уроков удалена — один показ в день вместо
  двух; строка «Забрать награду» переехала в полноэкранное окно.

**Чек-лист деплоя**: перед выкаткой клиента применить миграцию
`20260831120000_streak_by_lesson.sql` — без неё `bump_streak_on_lesson` отвечает
PGRST202 и серия перестаёт расти совсем (старый `touch_daily_login` больше
не единственный источник +1).

Наблюдать после релиза: закрывать день уроком сложнее, чем заходом —
заморозки начнут гореть чаще, а экран срыва станет частым. Если цена 2 билета
за заморозку окажется дорогой при новой частоте — менять в SQL.

## Код-сплиттинг бандла — план реализации (2026-07-11, не начато)

### Зачем (что даст)
- Сейчас весь JS — один файл `dist/assets/index-*.js` на **765 КБ** (gzip 222);
  Vite ругается предупреждением при каждой сборке. Обычный пользователь
  скачивает и парсит код canvas-редактора и админки (~4 200 строк —
  `src/features/canvas/` + `src/features/admin/`), которые видит только админ.
- После разбивки: основной бандл ожидаемо −20–35%, предупреждение Vite
  уходит, первый вход (особенно на телефоне по 3G) быстрее — меньше скачать
  и меньше распарсить. Точные цифры замерить до/после по выводу `npm run build`.

### Почему это безопасно именно здесь
`AdminV2` и `CanvasPage` статически импортируются РОВНО в одном месте —
`src/app/ShellV2.jsx` (проверено grep'ом). Больше никто из основного кода
их не тянет, значит `React.lazy` отделит их в отдельные chunk'и чисто.
Вкладка «Админ» рендерится только при `isAdmin`, canvas-оверлей — только
когда `canvasLesson != null`: у обычного пользователя эти chunk'и даже
не начнут скачиваться.

### Шаги

1. **Хелпер перезагрузки** — новый файл `src/shared/lib/lazyRetry.js`
   (~15 строк). Известная беда Vite: после деплоя старые chunk-хэши отдают
   404, и `import()` у пользователей с открытой вкладкой падает. Обёртка:
   один раз перезагрузить страницу при ошибке загрузки chunk'а
   (флаг в sessionStorage, чтобы не зациклиться):
   ```js
   export function lazyRetry(importFn, key) {
     return importFn().catch(err => {
       const k = `pithy_lazy_reload_${key}`
       if (!sessionStorage.getItem(k)) {
         sessionStorage.setItem(k, '1')
         window.location.reload()
       }
       throw err
     })
   }
   ```
2. **ShellV2.jsx**: заменить два статических импорта на lazy:
   ```js
   import { lazy, Suspense } from 'react'
   const AdminV2   = lazy(() => lazyRetry(() => import('../features/admin/AdminV2.jsx'), 'admin'))
   const CanvasPage = lazy(() => lazyRetry(() => import('../features/canvas/CanvasPage.jsx'), 'canvas'))
   ```
   Обернуть места рендера в `<Suspense fallback={...}>`:
   - вкладка Админ: fallback `<div className="shellV2Panel">Загрузка…</div>`
     (в стиле существующих заглушек, НЕ белый экран);
   - canvas-оверлей: fallback — тот же `.shellV2CanvasOverlay` с текстом
     «Загрузка редактора…», чтобы оверлей не мигал.
3. **Ничего больше не трогать.** Плеер, лента, профиль, рейтинг, гонка —
   пользовательское ядро, остаются в основном бандле (все вкладки
   смонтированы всегда — ленивость сломала бы прогрев ленты). CSS не
   разбивать: `index.css` глобальный, это отдельная задача, не в этом заходе.
4. **Проверка сборки**: `npm run build` → в `dist/assets` появились
   отдельные `AdminV2-*.js` и `CanvasPage-*.js`; основной `index-*.js`
   заметно похудел; предупреждение «chunks larger than 500 kB» исчезло
   (если нет — найти, кто ещё статически импортирует canvas/admin:
   `grep -r "features/canvas\|features/admin" src --include=*.jsx -l`).
5. **Проверка в превью** (dev-сервер `pithy-dev`):
   - гость: лента открывается, во вкладке Network НЕТ chunk'ов admin/canvas;
   - админ: вкладка «Админ» открывается (после короткого fallback),
     ✎ на схеме модуля открывает canvas-редактор; консоль без ошибок.
6. **Правила проекта**: поднять `APP_VERSION`; новый файл `lazyRetry.js`
   добавить строкой в `STRUCTURE.md`; в конце ответа — список файлов с
   итоговым числом строк; отвечать по-русски.

### Критерий готовности
Основной `index-*.js` < 500 КБ (предупреждение Vite исчезло), админ-функции
работают как раньше, гость не скачивает админ-код (видно в Network).

   │  Карточка прогрева → ПЛЕЕР (готов) → Итоги XP → назад на схему

3. **Капча Cloudflare Turnstile** — код готов, но выключен, пока нет ключа.
   Бесплатно: у Cloudflare Turnstile свободный тариф (до 1 млн проверок в
   месяц), переносить домен/DNS в Cloudflare НЕ нужно, карта не нужна;
   капча в Supabase есть и на free-плане.
   Порядок включения — сначала клиент, потом сервер (если наоборот, между
   двумя шагами вход у всех отвалится с «captcha protection: request
   disallowed»):
   1. Cloudflare → Turnstile → создать виджет, hostnames: боевой домен +
      `localhost`, режим Managed. Забрать **Site Key** (публичный) и
      **Secret Key** (секретный, в код не кладём);
   2. Vercel → Settings → Environment Variables → `VITE_TURNSTILE_SITE_KEY` =
      Site Key → Redeploy. Проверить: виджет виден, вход всё ещё работает
      (Supabase токен пока игнорирует). Локально — та же переменная в `.env.local`;
   3. Supabase → Authentication → Attack Protection → включить CAPTCHA,
      провайдер Turnstile, вставить **Secret Key** → Save. С этого момента
      токен обязателен для ВСЕХ auth-запросов проекта.
   Формы, которые шлют токен: вкладка «Войти» (`AuthTab`), регистрация там же
   (`RegisterForm`) и регистрация внутри урока (`panels/registration/RegistrationPanel`).
   Пока переменной нет — виджет не грузится и формы работают как раньше
   (`shared/lib/useCaptcha.js`). Домены Turnstile уже прописаны в CSP
   (`vercel.json`).
   **Побочный эффект:** E2E-тесты под логином (`e2e/auth.setup.js`) заполняют
   форму и капчу решить не смогут — после включения их надо либо гонять против
   отдельного тест-проекта Supabase без капчи, либо временно отключать.
   **Виджет поднимается только по нажатию кнопки** (с 3.2.1085): до нажатия
   «Войти»/«Зарегистрироваться» капчи на экране нет вообще. Раньше виджет
   рисовался при открытии формы и мог не нарисоваться вовсе (форма открывалась
   не сразу — например переходом из ленты по тапу на лайк) — тогда кнопка
   требовала «подтверди, что ты не робот», а подтверждать было нечего. Теперь
   форма вызывает `captcha.guard(...)`: виджет появляется, форма ждёт токен
   («Проверка...») и отправляется сама, повторно нажимать не нужно. Если виджет
   сломался — до двух автоматических перезапусков с паузой 1,5 с, потом
   подсказка с кодом ошибки и кнопкой «Повторить».
   **Без токена форму не отправляем** (с 3.2.1088, раньше было наоборот): если
   скрипт не загрузился, виджет отдал ошибку или 12 секунд молчит вообще,
   отложенная отправка отменяется и человек видит «Проверка "я не робот" не
   работает (код N) — без неё вход невозможен». Прежнее поведение («пускаем
   без токена, решает сервер») писалось, когда капча в Supabase была выключена;
   сейчас токен обязателен, запрос без него всегда возвращает `captcha
   protection: request disallowed (no captcha_token found)`, и человек получал
   невнятную ошибку про вход вместо правды. Коды Turnstile в консоли
   (`[captcha] …`): **110200 — домен страницы не в Hostname Management виджета**
   (самая частая: забыт `localhost`/`127.0.0.1` или превью-домен Vercel),
   600010 — челлендж не смог выполниться, 300xxx — сбой самого виджета.
   Следующее нажатие кнопки формы поднимает виджет заново со счётчиком
   автопопыток с нуля.
   **Исключение — живая капча ждёт галочку** (с 3.2.1086): если Turnstile позвал
   `before-interactive-callback`, таймаут снимается и форма ждёт человека
   сколько угодно. Иначе выходило так: через 12 секунд вход уходил без токена,
   ловил «captcha protection: request disallowed», и ровно в этот момент
   галочка загоралась зелёным. Там же: после ошибки сервера `reset()` снимает
   и флаг «капча не отвечает» — иначе следующее нажатие снова уходило бы без
   токена и получало ту же ошибку по кругу. С 3.2.1088 ошибка виджета гасит и
   `asking`: иначе подсказка продолжала врать «поставь галочку» после того, как
   галочка уже исчезла вместе со сломанным виджетом.
   **Выключить мгновенно** можно, убрав `VITE_TURNSTILE_SITE_KEY` из Vercel и
   передеплоив — виджет пропадёт (если капча в Supabase уже включена, её надо
   выключить там же, иначе вход перестанет работать).

## Перевод названия модуля: пословно + полностью (2026-07-25)

**Зачем**: в ленте название модуля = сама изучаемая фраза. Теперь по ней можно
разобрать перевод — как целиком, так и каждое слово отдельно.

**Как это выглядит у пользователя** (вкладка «Рекомендации»):
- Тап по слову фразы → слово подсвечивается лаймовой подложкой (текст тёмный),
  от него вверх под 45° растёт линия, ломается в горизонталь (параллельно низу
  экрана), и над горизонталью разворачивается подложка с переводом. Вся
  анимация быстрая (≈350 мс от тапа до готовой подсказки).
- Подложка перевода всегда в одном месте: по центру экрана по X и на одной
  высоте по Y (уровень отсчитывается от блока фразы, а не от самого слова) —
  от слова зависит только длина диагонали и горизонтали до центра.
- Повторный тап по тому же слову или тап по подсказке — закрыть. Тап по другому
  слову — старая подсказка исчезает, появляется новая.
- Под фразой — строка «раскрыть перевод ⌄» (полный перевод фразы). Она
  выкатывается из-под фразы после того, как шарики-спойлер разлетелись.
- Подпись «X уроков в модуле» переехала оттуда в кнопку «Изучить фразу» —
  теперь это чип прямо в кнопке.

**Где заполняется**: попап `ModuleTitleEditor` — из списка модулей в админке
(кнопка ✎) и по тапу на название в схеме модуля (админ). Там же название,
полный перевод и поле перевода под каждым словом; слова разбиваются
автоматически, знаки препинания игнорируются, при правке названия уже введённые
переводы не теряются.

**База**: `supabase/migrations/20260725140000_module_translations.sql` —
`curricula.title_translation` (text) и `curricula.word_translations`
(jsonb `[{"w":"слово","t":"перевод"}]` в порядке слов).
**Миграцию нужно применить** — до этого редактор скажет об этом прямым текстом,
а лента будет работать по-старому (список модулей читается запасным запросом
без новых колонок, переводов просто нет).

## Обмен уроком в JSON (канвас → анализ → шаблон)

**Зачем**: отдать урок целиком «наружу» — человеку или модели — так, чтобы по
нему можно было разобрать стиль автора и вернуть готовый шаблон следующего
урока, который подгружается обратно одним вставленным текстом.

**Где**: кнопка ⇄ в шапке холста → окно «Поделиться / Импорт»
(`src/features/canvas/lesson-io/`).

**Что уезжает**: весь сценарий — типы нод, их настройки, переходы между ними
(включая особые переходы по вариантам ответа), комментарии продакшена,
координаты. Медиа НЕ уезжает: у ноды остаётся пометка `needs` («сюда нужна
озвучка»), а всё, что считается из файла (волна, длительность, тайминги слов),
выбрасывается — редактор пересчитает это при загрузке файла.

**Формат**: `{ format: "pithy-lesson", version, lesson, legend, nodes[] }`.
Переходы ссылаются на `ref` («n1», «n2»), а не на внутренние uuid, поэтому файл
читается и пишется руками. `legend` — самодокументация: описание каждого типа
ноды, каждого поля и каждого условия перехода; её можно не прикладывать
галочкой, но по умолчанию она есть (без неё разбор будет гадать).

**Импорт**: «Заменить урок» или «Добавить к уроку». Ноды получают новые id,
номера пересчитываются по графу, координаты можно не указывать — раскладка
построится сама. Неизвестные типы и висячие ссылки не роняют импорт, а
попадают в список предупреждений.

**Решение**: формат обмена — единственный источник правды о том, что модель
видит об уроке. Появилось новое поле ноды — его нужно описать в
`lesson-io/lessonSchema.js`, иначе оно молча не доедет ни в разбор, ни в шаблон.

## Диагностика холста: связи, целостность графа, импорт

**Зачем**: связи на холсте могут «пропасть» по причинам, которых не видно
глазами — от битых данных до особенностей отрисовки в конкретном браузере.
Разбирать это на словах бесполезно, поэтому в канвас встроены инструменты.

**Что есть**:
- `[GRAPH]` в консоли — проверка целостности графа при каждой смене состава
  нод (`canvasIntegrity.js`): дубли id нод и триггеров, связи в никуда, дубли
  номеров. Молчит, пока всё в порядке. Дубли id — самая коварная поломка:
  связь ведёт «в никуда конкретно», и урок ломается и в редакторе, и в плеере.
- Меню «⋯» → **«Отладка связей»**: прямые отрезки поверх графа, HTML-метки
  портов мимо SVG, проба SVG из четырёх линий (простая / со сдвигом / со
  сдвигом и масштабом / с vector-effect) и подробный лог `[LINKS]`/`[DRAW]` —
  сколько связей в данных, сколько путей построено, что реально в DOM, какие у
  элементов атрибуты и попадают ли они в кадр.
- Меню «⋯» → **«Сжать раскладку»** (`canvasCompact.js`): длинная лента нод
  собирается «змейкой» в несколько рядов по порядку сценария. Меняются только
  координаты.
- Кнопка **🗑** в шапке — очистить урок целиком.
- `[IMPORT]`, `[NODE]`, `[LINK]` — что разобрал импорт, что создала кнопка
  и что с чем связала протяжка порта.

**Решение**: положение холста на экране перемеряется перед каждой протяжкой
(`measureBoard` в `CanvasBoard.jsx`). `ResizeObserver` ловит изменение размера,
но не сдвиг — а координаты мыши считаются именно от прямоугольника доски, и
устаревший кэш уводил тянущуюся связь мимо курсора.

**Чего в отрисовке связей делать не стоит**: `vector-effect: non-scaling-stroke`
и отсечение содержимого по кадру пробовались (3.2.1254–3.2.1266) и были
откачены — они ломали отображение связей. `CanvasConnections.jsx` намеренно
держится в том виде, в котором работает.

## Озвучка текста через ElevenLabs (TTS) — реализовано и работает (2026-09-02/03)

### Суть
В ноде `audio` («Голосовое сообщение») кнопка «🔊 Озвучить» рядом с текстовым
полем: генерирует mp3 из введённого текста через ElevenLabs API (сейчас —
фри-план с одним из стандартных голосов; в будущем — своя натренированная
модель голоса, замена одним секретом без правки кода).

### Как это устроено (важно — без промежуточных ссылок на ElevenLabs)
Генерация — **одноразовая, только в момент редактирования**. Итоговый mp3
полностью уходит в наш R2 (`pithy-files`), как и при ручной загрузке файла;
после генерации сервер ElevenLabs больше не участвует ни в показе урока
ученику, ни в скорости чата — плеер тянет файл из нашего R2/CDN точно так же,
как любое другое голосовое сообщение. Ожидание есть только один раз, в
канвасе, пока админ жмёт «Озвучить» (короткая фраза — обычно 1–4 сек).

### Решения (обсуждено с пользователем)
- **Голос**: один голос через серверный секрет `ELEVENLABS_VOICE_ID` (без
  выбора в UI на этом этапе) — смена на свою модель = замена одной переменной.
- **Повторная генерация**: клик «Озвучить» с изменённым текстом **перезаписывает**
  — старый файл удаляется из R2 (`deleteFromR2`), новый занимает его место в
  `node.typeData.audio`. Без хранения истории версий.
- **Лимит символов** (фри-план ElevenLabs, обычно ~10k/мес): в UI показывается
  остаток лимита (запрос к `/v1/user/subscription` ElevenLabs).
- **Предпрослушка в редакторе**: добавляется кнопка ▶ прямо в `NodeAudioPicker`
  — для быстрой проверки результата (и TTS, и ручной загрузки) без запуска
  всего сценария плеера. Уточнение по ходу обсуждения: сейчас в редакторе
  ноды предпрослушки НЕТ вообще — кнопка ▶ в `NodeHoverMenu.jsx` запускает
  весь сценарий с этой ноды («Пройти сценарий»), это другая функция. Новая
  кнопка ▶ в `NodeAudioPicker` — самостоятельная маленькая фича.

### Почему без отдельного шага транскрипции
Сейчас у ручной загрузки: файл → локально считается waveform/duration →
отдельно едет в edge function `transcribe-audio` (Whisper через Groq), которая
транскрибирует уже загруженный файл и выравнивает его с текстом, который
ввёл админ (даёт `wordTimings` для посимвольной печати в `AudioModule.jsx`).
Для TTS это не нужно: раз мы **сами** генерируем аудио из текста, ElevenLabs
может сразу отдать точные тайминги символов (`.../with-timestamps` endpoint)
— конвертируются в тот же формат `wordTimings: [{w, t}]`, шаг Whisper
пропускается полностью.

### Архитектура (пересмотрена при реализации 2026-09-02)
Важное открытие по ходу разработки: файлы урока в канвасе **не** грузятся в
R2 сразу при выборе — `useLessonFiles.js` держит их локально (IndexedDB +
`status: 'local'`) и заливает в R2/`files` только при явном синке урока
(`syncToServer`). Если бы `tts-elevenlabs` сама писала в R2, это ломало бы
единый паттерн (офлайн-правки, дедуп по хэшу перед заливкой, пакетный синк).
Поэтому от первоначальной идеи «функция сама льёт в R2» отказались:

- `supabase/functions/tts-elevenlabs/index.ts` (по образцу `transcribe-audio/
  index.ts`) — **только генерирует и возвращает**: секреты
  `ELEVENLABS_API_KEY`/`ELEVENLABS_VOICE_ID`/`ELEVENLABS_MODEL_ID`, зовёт
  ElevenLabs `.../with-timestamps`, конвертирует символьные тайминги в
  `wordTimings` (тот же формат, что даёт Whisper), отдаёт
  `{ audioBase64, contentType, wordTimings }`. R2/БД не касается вообще.
  Доступ только админу (`requireAdmin`, как у `r2-upload-url`) — квота
  ElevenLabs ограничена, анонимный ключ открыл бы её кому угодно.
- `supabase/functions/elevenlabs-quota/index.ts` — остаток лимита символов
  (`/v1/user/subscription`), тоже только для админа.

## Генерация фото через Gemini API — реализовано (2026-09-03)

По той же схеме, что TTS выше: в ноде `photo` кнопка «🎨 Сгенерировать» рядом
с отдельным полем-промптом (`typeData.photo.imagePrompt` — сознательно НЕ то
же поле, что `caption`: подпись — то, что видит ученик под фото, промпт —
только описание для генерации, ученику не показывается). Та же архитектура
«функция только зовёт внешний API и отдаёт base64, R2 не трогает» — регенерация
идёт через тот же `onPick`, что и ручной выбор файла (см. решение по TTS выше
про `useLessonFiles.js`/`syncToServer`).

Провайдер выбран НЕ Google Flow (`labs.google/fx/tools/flow`) — там нет
публичного API вообще, это чисто веб-интерфейс под подписку Google AI
Pro/Ultra. Вместо этого — **Gemini API**, модель `gemini-2.5-flash-image`
("Nano Banana"): у неё есть настоящий бесплатный лимит — 500 картинок/сутки
через ключ Google AI Studio, без привязки карты.

- `supabase/functions/generate-image/index.ts` (+ `deno.json`, по образцу
  `tts-elevenlabs`) — POST, только админ (`requireAdmin`). Секрет
  `GEMINI_API_KEY` (опционально `GEMINI_IMAGE_MODEL`, дефолт
  `gemini-2.5-flash-image`). Зовёт `POST .../v1beta/models/{model}:
  generateContent` с `{ contents: [{ parts: [{ text: prompt }] }] }`,
  достаёт из `candidates[0].content.parts[]` первую часть с `inline_data`
  (`{ mime_type, data }`) — формат подтверждён по официальному REST-референсу
  Gemini API (`ai.google.dev/api/generate-content`), не наугад, в отличие от
  ElevenLabs `.../with-timestamps` в своё время. Если модель отказала
  (например, политика безопасности) и вернула только текст — этот текст
  уходит в `error`, чтобы админ видел причину, а не молчаливый сбой.
- `src/shared/lib/imageGenApi.js` — `generateImage(prompt)` → декодирует
  base64 в `File` (png или jpg по `contentType`).
- `src/features/canvas/NodeImageGen.jsx` — своя textarea под промпт (не
  переиспользует `caption`), кнопка «🎨 Сгенерировать», `StatusTag` (тот же,
  что у NodeAudioTts, из NodeAudioPicker.jsx). При ошибке показывает текст
  причины под кнопкой (важно для отказов модели — не просто «⚠»). Повторная
  генерация удаляет старый файл ноды через `onRemoveOldFile`.
- `NodeContentEditor.jsx` — рендерит `NodeImageGen` рядом с `NodeMediaCrop`
  для типа `photo`. Продакшен-список уже прокидывает `onRemoveLessonFile` (см.
  выше про TTS) — регенерация фото в обоих редакторах ведёт себя одинаково
  без дополнительной прокидки.
- Квота: у Gemini API нет публичного эндпоинта «остаток лимита» (в отличие от
  ElevenLabs `/v1/user/subscription`) — индикатор остатка не показывается,
  это ограничение самого API, не недоделка.

### Gemini временно недоступен — free tier для image-моделей = 0 (открытие 2026-09-03)
Живая проверка сразу упёрлась в `429 RESOURCE_EXHAUSTED`, `limit: 0` для
`generate_content_free_tier_requests`. Это не «исчерпали лимит» — в декабре
2025 Google обнулил Free tier IPM (images per minute) именно для моделей
генерации изображений на всех проектах; включён он остаётся только у
текстовых моделей. Раньше в этом же разделе было написано «500 картинок/сутки
бесплатно» — это было верно до декабря 2025, сейчас устарело. Чтобы Gemini
заработал, на Google Cloud проекте нужно привязать биллинг (Tier 1) — без
минимального списания, просто как разрешение; дальше — оплата по факту,
$0.02–0.04/картинку. Отложено пользователем на будущее.

### Второй провайдер — Cloudflare Workers AI (решение 2026-09-03)
Пока Gemini на паузе, добавлен второй провайдер в ту же функцию
`generate-image` — переключение одним секретом `IMAGE_PROVIDER`
(`cloudflare` — новый дефолт, `gemini` — прежний путь, код сохранён и
рабочий, ждёт только биллинга). Выбор в пользу Cloudflare:
- **Настоящий бесплатный лимит** — 10 000 «нейронов»/сутки, без привязки
  карты вообще (не «биллинг включён, но $0 минимум», как у Gemini) —
  подтверждено официальной страницей pricing Cloudflare Workers AI.
- **Синергия с уже существующей инфраструктурой**: R2 (`pithy-files`) уже
  на этом же Cloudflare-аккаунте — account id общий для всех продуктов
  аккаунта, поэтому секрет `R2_ACCOUNT_ID` переиспользован для Workers AI,
  отдельный не заводился. Нужен только новый Cloudflare API-токен с правом
  Workers AI (R2-ключи для него не подходят — это разные системы доступа).
- Модель — `@cf/stabilityai/stable-diffusion-xl-base-1.0` (SDXL, входит в
  бесплатный бюджет нейронов).

Технический нюанс, отличающий Cloudflare от ElevenLabs/Gemini: успешный
ответ SDXL — не JSON+base64, а **сырые байты PNG** (`Content-Type:
image/png`) — подтверждено по официальной REST-документации Cloudflare.
Функция сама конвертирует их в base64 (`bytesToBase64`, чанками по 0x8000 —
`btoa(String.fromCharCode(...bytes))` на всём буфере разом падает на
картинках заметного размера), чтобы контракт с клиентом (`imageGenApi.js`,
`{ imageBase64, contentType }`) остался одинаковым для обоих провайдеров —
клиентский код и `NodeImageGen.jsx` не знают и не должны знать, какой
провайдер сейчас активен.

### Проверено вживую (2026-09-03) — два бага найдены и исправлены
Первая живая генерация через Cloudflare прошла (значит REST-формат SDXL и
конвертация в base64 — рабочие), но:
1. **Кнопка показывала «Gemini»** — `StatusTag label="Gemini"` был захардкожен
   в NodeImageGen.jsx ещё с версии на одном Gemini, до появления выбора
   провайдера. Клиент не должен знать/показывать, какой провайдер активен
   (это решается только секретом `IMAGE_PROVIDER` на сервере) — заменено на
   нейтральный `"AI"`.
2. **Результат на русском промпте — мимо запроса**: SDXL обучена в основном
   на английских подписях, кириллица на входе давала почти случайную
   картинку. Исправлено переводом на сервере: если в промпте есть кириллица,
   `generate-image` сначала зовёт `@cf/meta/m2m100-1.2b` (перевод, тот же
   Cloudflare-аккаунт, та же бесплатная квота) с `source_lang: ru,
   target_lang: en`, и уже переведённый текст уходит в SDXL. Если перевод не
   удался — идём с исходным текстом, не роняем всю генерацию.
3. **Промпт-поле визуально лепилось к контролам зума** фото (±/сброс у
   NodeMediaCrop) — переставлено: `NodeImageGen` теперь рендерится ДО
   `NodeMediaCrop` (сначала промпт и генерация, потом кроп готовой картинки —
   так и логичнее по смыслу действия), плюс у `.nodeImageGenWrap` появилась
   рамка и нижний отступ, чтобы блок читался отдельно от соседних контролов
   независимо от порядка.

Перевод кириллического промпта подтверждён рабочим (2026-09-03) — русский
текст больше не даёт случайную картинку.

## «🪄 Смонтировать» — авто-расстановка таймлайна диктанта (2026-09-03)

Реализовано (продолжение обсуждения выше — пользователь решил делать сразу).
Кнопка в шапке аудио-секции редактора таймлайна (рядом с «+ Добавить
аудио»/«✕ Убрать аудио»), видна только когда в таблице уже есть файл.

**Откуда тайминги слов** — не понадобилось ничего нового заводить: озвучка
таблицы сейчас всегда ручная загрузка (своей TTS-кнопки у table пока нет), а
`transcribe-audio` (Groq Whisper, `timestamp_granularities: word`) уже
существует и уже используется для эффекта печатания в аудио-нодах — просто
переиспользован тот же вызов на файле таблицы. Если/когда для table появится
своя TTS-генерация — тайминги придут от неё напрямую (ElevenLabs `.../with-
timestamps` уже отдаёт то же самое `{w,t}`), Groq тогда останется фолбэком
для ручной записи.

**Алгоритм** (`table-editor/autoMontage.js`, чистые функции, покрыты тестами
`autoMontage.test.js`): один проход по хронологическому списку слов озвучки;
на каждой позиции жадно ищем самую длинную ещё не найденную фразу среди всех
целей (текст ячейки/варианта ИЛИ слово ответа вне таблицы) — нашли, отмечаем
цель закрытой и прыгаем дальше за концом фразы; не нашли — просто идём дальше
(русские слова вокруг молча пропускаются). Ровно тот же принцип «жадно,
длиннее выигрывает», что уже был в `tableCellMatch.js` (deriveAnswerTokens)
для проверки ответа — не изобретал новый.

**Найденная и обработанная сложность**: ячейка-группа через запятую («he,
she, it») в реальной русской озвучке чаще звучит с союзом «и»/«или» вместо
запятой перед последним элементом («he, she **и** it») — искать фразу
целиком бесполезно. Разбирается на отдельные элементы группы, находится
ПЕРВЫЙ прозвучавший — это осознанное упрощение: черновой клип короче, чем
может быть «на самом деле» (не тянется до последнего элемента группы), но
конец всегда можно дотянуть руками на таймлайне — не пытался решить это
идеально автоматически, риск переусложнить не окупился бы для черновика.

**Кэш, а не пересчёт с нуля каждый раз**: тайминги слов сохраняются в
`tData.table.wordTimings` (то же поле по духу, что `waveformData`/`duration` —
попадает в FILE_FIELDS, из экспорта JSON вырезается автоматически, ничего
менять в exportLesson.js не пришлось). Повторный клик «Смонтировать» после
правки текста ячейки/сценария не бьёт в Groq снова — пересчитывает только
сопоставление на уже полученных таймингах. Кэш сбрасывается сам ТОЛЬКО когда
аудио реально заменили (`fileId` изменился), не при каждом открытии
редактора — реализовано через ref с предыдущим fileId, а не наивный `useEffect
на [fileId]` (тот стирал бы кэш сразу при маунте, до первого реального
использования).

**Не блокирует ручную правку** — ключевое требование пользователя. Результат
кнопки — это вызовы ТЕХ ЖЕ `updateClip`/`toggleHighlight`, что дёргает ручное
перетаскивание клипа мышью: никакого отдельного «авто-режима» или флага
«не трогать» на слое нет, данные неотличимы от выставленных руками. Перед
заменой уже существующей разметки — `window.confirm` (тот же паттерн, что у
`applyTemplate` в TableEditorModal.jsx — «Заменить текущую сетку шаблоном?
Несохранённые правки будут потеряны»).

**Нагрузка**: один сетевой вызов на Groq (несколько секунд, тот же путь, что
уже используется для аудио-нод — ничего нового для инфраструктуры) плюс
чистый JS-проход по словам (для типичной таблицы — до 20 ячеек, десятки слов
озвучки — миллисекунды, не заметно). Ничего не деплоилось — edge function
transcribe-audio уже существует и уже задеплоена.

### Найдено по логам: гонка обновлений typeData (2026-09-03)
Пользователь прислал реальный консольный вывод с включённым дебагом — и он
сразу назвал причину:
```
[TABLE TTS] pick {name: 'tts-....mp3', size: 94502, fileId: '49c2d7ea-...'}
[TABLE TTS] opening editor with {fileId: null, hasWordTimings: true}
```
`file_id` реально был получен и записан первым вызовом — но к моменту
открытия редактора он `null`, а `wordTimings` (записанные ВТОРЫМ, отдельным
вызовом чуть позже) — на месте. Это не проблема восстановления blob-URL
(вчерашний фикс), а гонка на уровень выше: **и `NodeTableTts`, и
`NodeAudioTts` патчат ноду в ДВА отдельных вызова подряд** — сначала
`onPick(file)` → `file_id`, потом (после `await analyzeWaveform`/
`probeAudioDuration`) отдельно `onAnalyzed(...)` → `waveformData/duration/
wordTimings`. `updateTypeData` в `NodeContentEditor.jsx` считал патч так:
`{ ...node.typeData, [node.type]: { ...tData, ...patch } }`, где `tData` —
СНИМОК из ЗАМЫКАНИЯ текущего рендера. Если оба вызова происходят до того,
как React успевает перерисовать компонент со свежими пропсами (а в этой цепи
почти всегда успевают — генерация занимает секунды, а `analyzeWaveform`/
`probeAudioDuration` на маленьком mp3 — миллисекунды, реального ре-рендера
между `onPick` и `onAnalyzed` часто просто не происходит), ВТОРОЙ патч
считается от того же СТАРОГО `tData` (без file_id) и полностью переписывает
`typeData[type]`, стирая то, что записал первый патч. `setNodes(prev => ...)`
в `updateNode` не спасало: сам `prev` был свежим, но передаваемый в него
`patch` — уже готовым объектом, посчитанным заранее от устаревшего снимка.

**Масштаб находки шире одной кнопки**: тот же паттерн «pick, потом отдельно
analyzed» используют `NodeAudioTts.jsx` (обычная озвучка аудио-ноды) и,
похоже, ручная загрузка аудио в `NodeAudioPicker.jsx` (там ДАЖЕ три
последовательных вызова: pick → waveform/duration → wordTimings от Whisper) —
это была скрытая гонка, ждавшая своего часа во всех трёх местах, просто
раньше никто не смотрел, доехал ли `file_id` до сохранённого узла после
генерации.

**Фикс — в корне, не патч на одном компоненте**: `updateNode` в
`CanvasBoard.jsx` и `updateTypeData` в `NodeContentEditor.jsx` теперь
поддерживают функциональную форму патча — `(node) => патч`, ровно как
функциональный `setState`. `updateTypeData` теперь ВСЕГДА строит патч как
функцию от АКТУАЛЬНОГО узла на момент применения (внутри `setNodes(prev =>
...)`), а не от снимка на момент вызова — так что сколько бы патчей подряд
ни прилетело до следующего рендера, каждый следующий видит результат
предыдущего. Плюс диагностику из прошлого раздела убрал — причина найдена,
дальше держать `dbg()`-заглушки в проде смысла нет.

### Таблица-диктор молчала в плеере: часы столбили старт за собой (2026-09-03)
После починки `file_id` файл доехал до плеера, но звука в прогоне так и не
было. Логи (`[td-file]`, `[td-auto]`) показали, что причина — НЕ политика
автозапуска браузера: ни `audio.play() отклонён`, ни `<audio> onError` в логе
нет вовсе, то есть `play()` даже не вызывался, хотя источник появился:
```
[td-file] ... localFile=есть ... → итог src=⚠ NULL (аудио не смонтируется)   ← рендер 1
[td-file] ... → итог src=blob:http://localhost:5173/abd038d6-...              ← рендер 2
[td-auto] аудио не стартовало за 3с — крутим таймлайн часами
```
Гонка в `useTableDictatorAutostart.js`. Blob-URL локального файла рождается в
эффекте, поэтому на ПЕРВОМ рендере `audioSrc` всегда `null` → `silentMode`
= `true` → эффект часов немедленно ставил `autoPlayFired.current = true`,
застолбив запуск. Через кадр приходил настоящий `audioSrc`, но аудио-эффект
видел поднятый флаг и молча выходил, а свой таймер часы отменяли собственным
cleanup (`silentMode` стал `false`). Не запускалось НИЧЕГО — прогон вытягивала
только 3-секундная страховка, и таблица шла молча, с задержкой.

Почему не всплывало раньше: у таблиц источником обычно был синхронизированный
`r2Url` — он есть уже на первом рендере, `silentMode` там сразу `false`.
Локальный, только что сгенерированный TTS-файл — первый случай, когда
источник появляется лишь со второго рендера. Побочно из-за этого не включался
и мини-спектр (HUD): `setHudVisible(true)` живёт в аудио-эффекте.

**Фикс**: флаг поднимается в МОМЕНТ фактического старта часов (внутри таймера,
после повторной проверки), а не при планировании. Тогда пришедший через кадр
звук успевает перехватить старт, а если источника так и нет — часы стартуют
через те же 800мс, как и раньше. Добавлена строка лога на случай, когда звук
приходит уже после старта прогона (файл раскрылся позже 800мс) — деградация
допустимая, но теперь видна. Регресс закрыт тестом в `tableDemo.test.js`.

### Печать голосового разъезжалась со звуком (2026-09-03)
Текст в аудио-сообщении печатается посимвольно под звук: `AudioModule` считает
время каждого символа, `PlayerTypingText` показывает первые N символов. Нашлись
три независимые причины расхождения — все три починены.

1. **Тайминги считались не по тому тексту.** Массив строился по реконструкции
   `text.trim().split(/\s+/)` — по одному элементу на букву плюс один на
   разделитель, то есть под строку «слова через ОДИН пробел». Печать же режет
   настоящий `text`. Любой двойной пробел, пустая строка между абзацами или
   отступ в начале сдвигали печать относительно звука, и сдвиг копился к концу
   сообщения. Плюс на озвучку уходит `text.trim()`, а печатается непотриммленный
   текст — ещё один источник той же ошибки.
2. **Слова сопоставлялись по индексу**: i-е слово текста = i-й тайминг.
   ElevenLabs нормализует произносимое (числа, сокращения), Whisper
   расшифровывает на слух — стоило числу слов разойтись, и весь остаток
   сообщения печатался по чужим временам.
3. **Округление до десятых в `tts-elevenlabs`**: `Math.round(t*10)/10` давало
   дрожание ±50мс на каждом слове — печать то опережала звук, то отставала.

Расчёт вынесен в `src/shared/lib/charTimings.js` (`buildCharTimings`): позиции
слов берутся прямо из текста (`matchAll(/\S+/g)` — индекс совпадения), слова
сопоставляются по написанию (регистр и пунктуация не мешают) с окном на
пропуск, неопознанные получают время интерполяцией между соседями, а вовсе
чужие тайминги дают ровную раскладку вместо рывков. Разделители любой длины
теперь ничего не сдвигают, потому что считаются по факту, а не достраиваются.
Округление в edge function — до сотых. Покрыто `charTimings.test.js`.

**Важно**: правка `t` до сотых лежит в edge function — она подействует только
после `supabase functions deploy tts-elevenlabs`. Уже сгенерированные тайминги
остаются округлёнными до 0.1с (перегенерировать озвучку, если мешает); две
первые причины чинятся сразу, без деплоя и без перегенерации.
